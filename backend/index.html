1
User Login / Signup Flow
1
User enters credentials in Flutter App
User fills email and password in login/signup form
{ email: "user@example.com", password: "secure123" }
2
Flutter sends credentials to Supabase Auth
Direct connection - bypasses Rust backend
POST https://[project].supabase.co/auth/v1/signup
POST https://[project].supabase.co/auth/v1/token?grant_type=password
3
Supabase validates credentials
Checks if user exists, verifies password hash
4
Supabase returns JWT tokens
Access token (1 hour expiry) + Refresh token (longer expiry)
{
"access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
"refresh_token": "v1-refresh-token-xyz",
"user": { "id": "user-id-123", "email": "user@example.com" }
}
5
Flutter stores tokens securely
Uses flutter_secure_storage or similar package
💡 JWT Token Content
The JWT token contains: user_id (sub), email, expiration time (exp), role (authenticated), and is cryptographically signed by Supabase. This signature cannot be forged without Supabase's secret key.

2
Get User's Calendar Events
6
Flutter requests events from Rust API
Includes JWT token in Authorization header
GET https://your-app.fly.dev/events
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
7
Rust backend extracts JWT token
Uses TypedHeader<Authorization<Bearer>> extractor
let user_token = auth.token();
8
Rust forwards request to Supabase
Passes user's JWT token (not service key!)
GET https://[project].supabase.co/rest/v1/calendar_events?select=*
apikey: [supabase_anon_key]
Authorization: Bearer [user_token]
9
Supabase validates JWT signature
Verifies token was created by Supabase, not tampered with
10
Supabase extracts user_id from token
Reads the "sub" claim from validated JWT → auth.uid()
auth.uid() = "user-id-123"
11
RLS Policy automatically filters data
Database-level security ensures user only sees their events
SELECT * FROM calendar_events
WHERE user_id = auth.uid() -- Automatic filter!
12
Supabase returns filtered events
Only events where user_id matches the token's user_id
[
{ "id": 1, "user_id": "user-id-123", "title": "Tennis Match", ... },
{ "id": 5, "user_id": "user-id-123", "title": "Basketball", ... }
]
13
Rust backend forwards response to Flutter
Simply passes through the JSON array
14
Flutter displays events in UI
Calendar widget shows only user's events
🔒 Security: Why Other Users' Data is Protected
Even if an attacker tries to modify the user_id in the request, they CANNOT access other users' data because:
• user_id comes from the JWT token's signature, not user input
• JWT signature is validated - tampering invalidates it
• RLS policies enforce filtering at database level
• Attacker cannot forge Supabase's signature without the secret key

3
Create New Calendar Event
15
Flutter sends create event request
User fills form, Flutter sends to Rust API with JWT token
POST https://your-app.fly.dev/events
Authorization: Bearer [user_token]
{ "title": "Tennis Match", "start_time": "2026-01-25T14:00:00Z", ... }
16
Rust extracts token & forwards to Supabase
No need to manually add user_id - Supabase handles it!
POST https://[project].supabase.co/rest/v1/calendar_events
Authorization: Bearer [user_token]
Body: { "title": "Tennis Match", ... }
17
Supabase validates JWT & extracts user_id
Automatically adds user_id from token to the new row
18
RLS Policy checks INSERT permission
Verifies: auth.uid() = user_id in the new row
CREATE POLICY "Users can create their own events"
FOR INSERT WITH CHECK (auth.uid() = user_id)
19
Database inserts event & returns it
New event with auto-generated ID and timestamps
{ "id": 10, "user_id": "user-id-123", "title": "Tennis Match", "created_at": "..." }
20
Rust forwards response → Flutter displays it
New event appears in calendar immediately

4
Token Refresh (After 1 Hour)
21
Access token expires
JWT tokens typically expire after 1 hour for security
22
Flutter detects expired token
API returns 401 Unauthorized, or Flutter checks expiry time
23
Flutter sends refresh token to Supabase
Direct call to Supabase Auth (not through Rust backend)
POST https://[project].supabase.co/auth/v1/token?grant_type=refresh_token
{ "refresh_token": "v1-refresh-token-xyz" }
24
Supabase validates refresh token & issues new access token
Returns fresh JWT with new expiry time
{ "access_token": "eyJ...[new token]...", ... }
25
Flutter stores new token & retries failed request
User continues seamlessly without re-login

🎯 Key Architectural Decisions
1. Authentication: Flutter → Supabase Auth directly (no backend involvement)
2. API Calls: Flutter → Rust Backend → Supabase Database
3. Security: Forward user's JWT to Supabase, let RLS enforce access control
4. Simplicity: Rust backend doesn't validate JWT - Supabase does
5. Defense in Depth: Database-level security (RLS) protects even if app code has bugs
